  アクセストークン vs リフレッシュトークン (Supabase)

   * アクセストークン (JWT):
       * 寿命: 短い（例: 1時間）。
       * 役割: ユーザーの身分証明書。
       * 速度:
         署名を検証するだけで良いため、データベースへの問い合わせが不要で高速です（「サーバーが何か処理して終わり」という理解で合って
         います）。
   * リフレッシュトークン:
       * 寿命: 長い。
       * 役割: アクセストークンが切れた時に、新しいものを再発行するための引換券。
       * 安全性: 基本的に一度しか使えず、新しいトークンを取得する際にDBチェックが入るため安全です。

  1. なぜ2つに分けるのか？（セキュリティとパフォーマンスのジレンマ）

  Webアプリには常に2つの相反する要求があります。

   1. パフォーマンス:
      ユーザーがクリックするたびに、毎回データベースに「この人、ログインしてる？」と聞きに行くと遅いし、データベースがパンクする。
   2. セキュリティ: もしスマホを落としたり、ハッキングされたら、管理者が即座に「強制ログアウト」させたい。

  この2つを解決するために役割分担をしました。

  🛡️ アクセストークン (JWT: JSON Web Token)
   * 役割: 「短期通行証」。
   * 中身: ユーザーIDや有効期限が暗号署名付きで書かれたJSONデータ。
   * 特徴: ステートレス（DBを見ない）。
      
  サーバーは、送られてきたトークンの署名を計算で検証するだけです。「正規の署名がある＝改ざんされていない＝信用できる」と判断します。DB  への問い合わせが発生しないため、超高速にAPIを叩けます。
   * 弱点: 一度発行すると、有効期限（例:
     1時間）が切れるまでサーバー側から無効化できません。仮にその1時間の間にユーザーのアカウントをBANしても、トークンを持っている間はア
     クセスできてしまいます。だからこそ、寿命を短くする必要があります。

  🔄 リフレッシュトークン
   * 役割: 「通行証の再発行引換券」。
   * 特徴: ステートフル（DBを見る）。
      これを使ってアクセストークンを再発行する時、Supabaseは必ずデータベースの `auth.sessions` テーブルなどをチェックします。
   * 強み:
     ここでサーバー側の制御が効きます。もしユーザーがBANされていたり、パスワードが変更されていたら、サーバーは「再発行拒否」を出せます
     。これにより、アクセストークンの寿命（1時間）が尽きた時点で、確実に侵入者を締め出せます。

  2. 「リフレッシュトークンローテーション」という罠

  SupabaseなどのモダンなAuth基盤には「ローテーション」という強力なセキュリティ機能があります。これが「リフレッシュトークンがより安全」
  と言われる真の理由の一つです。

  仕組み:
  リフレッシュトークンは「1回使ったら捨てて、新しいものと交換する」使い捨て方式です。

  シナリオ:
   1. ハッカーがあなたのリフレッシュトークン（A）を盗んだとします。
   2. あなた（正規ユーザー）がサイトを使おうとして、裏でトークン（A）を使ってリフレッシュを試みます。
       * サーバー：「OK、新しいトークン（B）をあげるね」
   3. ハッカーが盗んだトークン（A）を使ってリフレッシュを試みます。
   4. サーバーの検知: 「あれ？ トークン（A）はさっき使われた済み（Used）だぞ？ これは盗まれた可能性がある！」

  結末:
  サーバーはそのトークン（A）から派生した全てのトークン（Bも含む）を即座に無効化（Revoke）し、強制ログアウトさせます。
  これにより、ハッカーだけでなく正規ユーザーもログアウトになりますが、「不正利用を検知してアカウントを守る」ことができます。これがCook  ieに保存しているだけではできない、リフレッシュトークンならではの防御策です。

  3. Next.js App Routerでの実際の動き

  今回のプロジェクト（cookie-dealer）では、この複雑なやり取りを以下のように処理しています。

   1. ブラウザ: 何も知りません。ただ Set-Cookie
      ヘッダーに従って、暗号化された箱（Cookie）を大事に持っているだけです。JavaScriptで中身を読む必要は一切ありません。
   2. Middleware / Server Actions:
      ユーザーがページを移動したりアクションを起こすたびに、Cookieがサーバーに飛びます。
      Next.jsのサーバーサイド（middleware.ts や
  utils/supabase/server.ts）で、「あ、アクセストークンの期限が切れそうだ」と判断すると、裏側でSupabaseと通信し、新しいアクセストークン
  とリフレッシュトークンをもらい、新しいCookieとしてブラウザにセットし直します。

  まとめ

   * アクセストークン: 「DBを見ないで高速処理するため」に存在するが、止められないので短命にする。
   * リフレッシュトークン: 「定期的にDBで生存確認するため」に存在し、セキュリティの最後の砦となる。
   * Cookie管理: これらをHttpOnly

     。

  2. auth.uid() と profiles テーブルの安全性

  「UUIDを平文で保存して大丈夫？」という疑問ですが、大丈夫です。

   * UUID（ユーザーID）は「口座番号」のようなもの
      誰かに知られても、それだけで勝手にお金を引き出されることはありません。
   * アクセストークン（JWT）は「銀行印/キャッシュカード」
      これが盗まれるとアウトです。

  攻撃者の視点:
  仮にハッカーが profiles テーブルを覗き見て、「AさんのUUIDは abc-123 だな」と知ったとします。
  しかし、ハッカーがサーバーに「私は abc-123 です」と主張するには、`abc-123`
  と書かれた上で、Supabaseの「秘密のハンコ」が押されたトークンを提示しなければなりません。
  ハッカーはハンコ（JWT Secret）を持っていないので、そのトークンを偽造できません。

  したがって、UUID自体は露出しても（極論、WebサイトのURLに含まれていても）セキュリティリスクにはなりません。 守るべきはトークンです。

  3. 「中がザル」ではない理由（RLSの鉄壁）

  Supabase（PostgreSQL）の内部では、auth.uid() を使ってさらに厳重なチェックが行われています。これを RLS (Row Level Security)
  と言います。

   1. Next.jsサーバー: トークンをSupabase等のDBへそのまま渡します。
   2. Supabase (DB): 受け取ったトークンの「ハンコ」を検証し、中からUUIDを取り出します。これが auth.uid() という関数の中身になります。
   3. RLSポリシー:
      「profiles テーブルの id 列が auth.uid() と一致する行しか読み書きさせない」というルール（Policy）をDB自体に設定します。        

   1 -- イメージ
   2 CREATE POLICY "自分のデータしか見れない"
   3 ON profiles
   4 FOR SELECT
   5 USING ( id = auth.uid() );

  これにより、たとえサーバーサイドのコードにバグがあっても、「認証された本人（トークンを持つ人）以外のデータは、DBレベルで絶対に出てこ
  ない」という安全性が担保されています。

  まとめ

   * 秘密鍵: Supabaseとサーバー（正しくは検証側）は共通のルール（秘密鍵）で「ハンコの正しさ」を確認し合っている。
   * UUID: 住所や口座番号と同じで、知られても「なりすまし」はできないので平文保存でOK。
   * 安全性: 「トークンの署名検証」と「DBのRLS」の二重構造で守られている。

> アクセストークンは、jwt
  secretがおされたuuidなどがさらに暗号化されているということ？暗号化は数学の素数を使っていると認識しているけど、トークンはどうなってい
  るの？具体的にどのような数学を使うの？

✦ 重要な区別があります。JWT（アクセストークン）において、「署名（Signing）」と「暗号化（Encryption）」は全く別のプロセスです。        

  通常、Supabaseや多くのWeb認証で使われるJWTは、「暗号化」されていません。 ただ「署名」されているだけです。

  1. 「暗号化」と「署名」の違い

   * 暗号化: 中身を隠すこと。鍵がないと読めない。
       * 例: 金庫に入れる。
   * 署名: 中身は見えるが、「改ざんされていないこと」を証明すること。
       * 例: 透明な袋に入れて、袋の口を「割り印」で封印する。中身（UUIDなど）は外から丸見えです。

  衝撃の事実:
  あなたのJWTアクセストークンをBase64デコード（ただの翻訳）すると、誰でも中身（UUIDやメールアドレス）を読めます。
  （※だからこそ、JWTの中にはパスワードやクレジットカード番号などの秘密情報を絶対に入れてはいけません）

  2. トークンはどうやって作られているの？ (HMAC-SHA256)

  Supabaseのデフォルト（HS256）では、ハッシュ関数を使っています。素数を使う「公開鍵暗号（RSAなど）」とは少し違う、もっと高速な数学です
  。

  料理に例えるとわかりやすいです。

  材料:
   1. Header: 「オレはHS256で署名するぜ」という宣言。
   2. Payload: 中身のデータ（UUID: 1234, Exp: 1時間後）。
   3. Secret: Supabaseとサーバーしか知らない秘密の合言葉（例: "super-secret-key"）。

  手順 (署名の作成):

   1. HeaderとPayloadを混ぜます（文字列として連結）。
   2. そこにSecret（合言葉）も混ぜます。
   3. これらをハッシュ関数（SHA-256）というミキサーにかけます。

  ハッシュ関数の魔法:
  どんなに長いデータでも、ミキサーにかけると必ず「意味不明な固定長の文字列（ハッシュ値）」になります。
   * 特徴1: 不可逆。 できたジュースから元の野菜には戻せません。
   * 特徴2: 雪崩効果。 材料が1文字でも違うと、全く違う味（ハッシュ値）になります。

  この出来上がった「ハッシュ値」が、トークンの3つ目のパーツ「署名（Signature）」になります。

  トークン全体 = Base64(Header) . Base64(Payload) . Signature

  3. 検証の数学（どうやってバレるか）

  ハッカーがUUIDを 1234 から 9999 に書き換えて（改ざんして）、サーバーに送りつけたとします。

  サーバー側の検証プロセス:

   1. 送られてきたトークンの Header と、改ざんされた Payload(UUID:9999) を取ります。
   2. サーバーも同じSecret（合言葉）を持っているので、手元で同じようにミキサー（ハッシュ関数）にかけます。
       * Header + Payload(9999) + Secret → 新しい署名B
   3. 送られてきたトークンにくっついている元の署名Aと、今計算した新しい署名Bを比較します。

  結果:
  元の署名Aは Payload(1234) と Secret で作られた味です。
  ハッカーは Secret を知らないので、Payload(9999) に合う正しい署名を作れません。        
  当然、署名A と 署名B は全く違う値になります。

  サーバー：「計算結果が合わない！ こいつ、中身を書き換えたな？ 却下！」

  これが、中身が丸見えでも「改ざんできない」理由であり、DBを見なくても「Supabaseが発行したままの状態である」と証明できる数学的トリック
  です。

✦ はい、アクセストークンはそのような「署名付きのValue」を持つCookieです。

  こちらはアクセストークンとは仕組みが全く異なり、「単なるランダムな文字列（不透明なトークン）」であることが一般的です。

  1. リフレッシュトークンの正体
  アクセストークン（JWT）のように「中にデータが入っている袋」ではありません。
  ただの「長い整理番号」です。

   * 例: 4fG7...z9q （ランダムな40〜60文字くらいの文字列）

  この文字列自体には何の意味も情報も含まれていません。デコードしても何も出ません。

  2. 通信と検証の流れ

  ユーザー（Next.jsサーバー）が「新しいアクセストークンをください」とSupabaseにお願いする時の流れです。

   1. 送信:
      Next.jsサーバーは、持っているリフレッシュトークン 4fG7...z9q をSupabaseへ送ります。

   2. Supabase側の処理 (DB検索):
      Supabaseは、受け取った文字列をキーにして、自身のデータベース（auth.refresh_tokens などのテーブル）を検索します。

       * 検索クエリのイメージ:
          SELECT * FROM refresh_tokens WHERE token = '4fG7...z9q'

   3. 検証:
      DBの中にそのトークンが存在し、かつ以下の条件を満たすかチェックします。
       * 有効期限は切れていないか？
       * 無効化（Revoked）フラグが立っていないか？
       * 親トークン（以前のリフレッシュトークン）と系譜が合っているか？

   4. 結果:
       * OKなら:
           1. 新しいアクセストークン（JWT）を作成・署名します。
           2. 新しいリフレッシュトークンを生成します（例: New8...k2L）。
           3. 古いリフレッシュトークン 4fG7...z9q をDB上で「使用済み」または「削除」にします（ローテーション）。
           4. 両方のトークンをセットにして返します。

       * NGなら:
          エラー（401 Unauthorized）を返し、強制ログアウトさせます。

  3. なぜリフレッシュトークンはJWTじゃないの？

  「即時停止（BAN）」させたいからです。

   * JWT (アクセストークン):
      発行したが最後、有効期限までは誰にも止められません（DBを見ないから）。
   * ランダム文字列 (リフレッシュトークン):
      使うたびに必ずDBを見ます。
      
  つまり、管理者が「こいつ怪しいな」と思ってDB上のそのトークンを削除したり「無効」フラグを立てれば、次の更新タイミングで確実にブロック
  できます。

  まとめ

   * アクセストークン (Cookie: access_token):
       * 中身：署名付きデータ (JWT)
       * 処理：計算だけ（DB見ない）
       * 目的：スピード重視
   * リフレッシュトークン (Cookie: refresh_token):
       * 中身：ただのランダム文字列（整理番号）
       * 処理：DB照合必須
       * 目的：管理・セキュリティ重視（ここが生命線）

> なぜリフレッシュトークンは意味のない羅列なの？ハッカーがそれを盗んで、アクセストークンのほうがexpiredしたからないんですよと言ってリ 
  フレッシュのほうだけ刺したしてきたらど却下するの？

✦ 鋭い指摘です。「意味のない羅列なら、誰が持ってきたってわからないじゃないか？」ということですね。

  結論から言うと、リフレッシュトークン単体で来た場合、「誰のトークンか」はDBを見ればわかりますが、「持ってきたのが本人か」はわかりませ
  ん。
  ですので、「持ってきた奴＝本人」とみなすしかありません。

  これがリフレッシュトークン最大の弱点です。
  もしハッカーにリフレッシュトークン（整理番号）を盗まれたら、ハッカーは「有効期限切れちゃってさ～」と窓口に来た本人になりすまして、新
  しいアクセストークンとリフレッシュトークンをゲットできてしまいます。

  これを防ぐための仕組みが、先ほど少し触れた「リフレッシュトークン・ローテーション（使い捨てシステム）」です。

  ---

  ハッカー vs システム（防衛戦）

  ハッカーがリフレッシュトークンを盗んだ後の攻防を見てみましょう。

  前提:
  ユーザー（Aさん）のリフレッシュトークン Token-1 が、何らかの方法でハッカーに盗まれました。

  1. ハッカーの攻撃（なりすまし成功）
  ハッカーは盗んだ Token-1 を使ってSupabaseにアクセスします。
   * ハッカー：「期限切れちゃった。更新して」
   * Supabase：「（DB照合... Token-1 は有効だな）はい、新しいアクセストークンと、次のリフレッシュトークン Token-2 だよ」
   * Supabase内部：「Token-1 はもう使用済みだからね。破棄！」

  ハッカーはこれでログイン状態になり、やりたい放題できます。ここまでは防げません。

  2. 正規ユーザーの反撃（検知の瞬間）
  しばらくして、本物のAさんのブラウザも、自動的に「期限切れちゃった。更新して」とSupabaseにアクセスします。
  Aさんのブラウザが持っているのは、まだ Token-1 のままです。

   * Aさん：「更新して（提示：Token-1）」
   * Supabase：「ん？ 待てよ。Token-1 はさっきハッカー（誰か）が使って、もう『使用済み』になっているはずだぞ？」

  3. Supabaseの緊急防御（全削除）
  Supabaseはこう判断します。
  「使用済みのチケットがもう一度持ち込まれたということは、このチケットは複製（盗難）されている！ 危険だ！」

   * Supabase：「緊急事態発生！ `Token-1` から派生した未来のトークン（ハッカーが持っている
     `Token-2`）も含めて、Aさんのトークンチェーンを全部無効化（Revoke）する！」

  4. 結末
   * Aさん: 更新に失敗し、ログアウトされます（再度ログインが必要）。
   * ハッカー: さっき手に入れた Token-2 を使おうとしても、すでにサーバー側で無効化されているため、突然使えなくなります。

  ---

  結論

   * なぜ意味のない羅列？
      DBのインデックスキーとして機能すれば十分だからです。
   * 盗まれたらどうする？
      
  最初の1回は使われてしまいます。しかし、「本人が使い終わった後のゴミ（古いトークン）」をハッカーが使おうとしたり、逆に「ハッカーが使 
  った後のゴミ」を本人が使おうとした瞬間にバレます。

  この「後出しで気づいて全員道連れにする」仕組み（ローテーションと再利用検知）によって、被害を最小限に食い止めています。
